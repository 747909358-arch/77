# 四版本提示词编译规范

## 1. 核心原则

四个版本不是四次独立创作，而是从同一个 canonical prompt data 编译而来。四个版本必须表达同一组有效规则、主题、边界和交付要求。

## 2. 四种必需交付

1. **中文 JSON**：结构化生成任务数据，中文字段说明/内容；必须合法 JSON。
2. **English JSON**：与中文 JSON 字段结构一一对应，视觉术语专业准确，不做生硬逐字翻译。
3. **中文简易提示词**：便于快速复制，压缩解释但保留核心 DNA、主题关系和必要约束。
4. **自然语言提示词**：将有效规则编译成适合目标后端的连贯、具体、可执行指令。

## 3. 两种 JSON 不得混淆

- 完整 `style_profile`：存档用，包含十三系统、证据、规则、依赖、边界和版本。
- 六字段生成 JSON：任务用，包含 `style`、`character`、`environment`、`narrative`、`mood`、`technical`。非人物任务可在 character 字段使用通用主体描述，或按 Schema 约定映射；六字段是简化表达，不是所有图像的必填本体。

## 4. 生成指令组织顺序

图像任务与交付要求 → 核心风格关系 → 主体及内容联系 → 空间与尺度 → 色光与表现 → 密度与锚点 → 文字要求 → 必要排除项。

## 5. 三条编译原则

- 精确词优先于情绪词：将“高级、温柔、梦幻”等转译成可观察的视觉参数。
- 结构化组织优于关键词堆砌。
- 意图说明 + 变量参数双轨：保留叙事意图，同时明确光线、色彩、构图、材质等变量。

## 6. 四版本一致性校验

检查风格核心、主题主体、数量/动作、规则优先级、允许变化项、排除项、文字、画幅和技术交付是否一致。中英文语义不得冲突。简易版允许压缩，但不得声称与完整版本信息完全等价；被压缩的关键项必须保留。

## 7. 正向与负向约束

先说明需要出现的表现，再针对参考偏移、明确限制或已观察失败编写排除项。负向要求必须注明作用对象，不无限追加抽象否定词。后端没有独立负面提示接口时，将必要限制放入实际接受的文本。

## 8. 后端编译

JSON 不是任一图像模型的通用 API。若后端不直接接受 JSON，必须先转译成它实际接受的自然语言或接口输入。记录实际提交文本，不能仅保存中间 JSON。
